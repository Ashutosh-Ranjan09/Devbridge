04The arithmetic, four skills

Every state starts at the prior θ₀ = 0.25, σ₀ = 1.30 in logit space. Each event contributes an observation with variance σ²ᴏʙs = 0.10 / (ρ × relevance × strength); between events the variance grows and μ drifts back toward the prior.

The self-report does almost nothing, and that is the design working

The C++ claim arrives with σ²ᴏʙs = 1.667 — eleven times the variance of the Codeforces event — so K = 0.124 and it shifts the score by +0.004. A candidate cannot talk their way up a skill they have evidence for, and cannot talk their way up one they have no evidence for either: numpy, which has only a bare claim, lands at 0.173 against a floor of 0.083.

05Propagation, at read time

Each neighbour enters as one more observation, with its variance inflated by 1/γ. Only states with direct evidence may act as a source, so this is a single pass with no cycles.

Edgeγσ²ᴏʙsKTarget score
typescript →PREREQUISITE_OF→ javascript0.550.4560.5810.256 → 0.350
react →REQUIRES→ javascript0.650.8630.2350.350 → 0.341
nextjs →REQUIRES→ react0.650.5120.5230.214 → 0.293
cpp →RELATED_TO→ c0.400.5170.7660.083 → 0.378

JavaScript is the interesting one. It has weak direct evidence (16.9 % of one repository, relevance 0.58, score 0.256), then receives TypeScript at K = 0.581 and React at K = 0.235 — the second contributing little precisely because the first already tightened the band. Note the React edge lowers the score marginally, which is correct: React is a weaker state than TypeScript, so it pulls the mean down while still narrowing the variance.

What the trace surfaced: propagation into an empty node is too generous

c has no direct evidence at all, yet lands at 0.378 — fifth overall, above JavaScript, Next.js and Python, all of which have real evidence. The cause is structural rather than a bug: a skill with no evidence carries the prior variance of 1.69, so even a heavily damped neighbour produces K = 0.766. Bayesian updating is behaving correctly; the presentation is not.

Two responses, both cheap. The SkillState schema already carries a propagated block — populate it, and have the query API list inferred skills separately rather than ranked among measured ones. Then let the sweep decide whether RELATED_TO at 0.40 is too generous; the wide band on c (σx 0.629, the widest of any scored skill) suggests it is. Do not fix this by clamping the score — that would hide the uncertainty rather than report it.

A single repo_artifact event for TypeScript on 2028-08-24 — 97 commits, ordinary substance, the same ×0.6 unverified-ownership cap. Nothing exceptional.

Nothing is re-earned

Two years of silence cost 0.147. One commit returned 0.149, landing at 0.382 against an original 0.381. This is the whole argument for modelling decay as growing variance: a "subtract points over time" scheme would have left this candidate slowly climbing back up a ladder they had already climbed. Here the band simply closes — σx 0.685 → 0.481 — and the estimate was never in doubt, only our confidence in it.

09Reproducing this

Every number in this document comes from contracts/reference/m6_model.py with the constants in contracts/m6-parameters.yaml, run over docs/docs/examples/report-full.json. Nothing was hand-computed and nothing was tuned to make this trace look good.

Three things to lift straight into the implementation:

  1. The eight-event batch is fixture two. Fixture one is the committed evidence-events.json; this one is derived from a full report and exercises the projection as well as the model.
  2. The step tables in §04 are unit tests. Pin K, μx and σx at each step, not just the final score — a wrong observation variance still produces a plausible-looking final number, and only the intermediate values catch it.
  3. The c behaviour in §05 is the first sweep target. It is the one place this trace found the model doing something defensible in the arithmetic and wrong in the presentation.
