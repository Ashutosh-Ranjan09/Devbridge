M5 Integration Spec

The concrete artefact both tracks build against: exact schemas, exact endpoints, the stack, and the order to do things in. Everything here is settled before implementation starts, because everything here is expensive to change afterwards.

Request lifecycle

client → POST /v1/verifications          (document + optional signals)
        ← 202 { verification_id, status: "queued" }

worker picks up the job:

  1. POST cvv-understanding/v1/extract   { document_ref }
     → ClaimGraph

  2. POST cvv-judgement/v1/evaluate      { claim_graph, external_signals? }
     → FindingsReport

  3. POST cvv-understanding/v1/narrate   { findings_report }
     → Narrative

  4. assemble → VerificationReport → persist → fire webhook

client → GET /v1/verifications/{id}      ← 200 VerificationReport
Why the flow is A → B → A

Narrative rendering happens last because it can only describe findings that already exist. It stays in A's service because it is an LLM call and A owns every LLM call — but it takes only the FindingsReport as input, never the document or the ClaimGraph. That input restriction is what makes it structurally impossible for the narrative to introduce a fact nobody computed.

The one rule about packages/cvv_contracts

Both services import it; neither service redefines any model in it. A change here is a change to the contract — it needs both people, a version bump, and regenerated fixtures. Set this expectation in week 1, because the failure mode is silent: one person adds a field locally, the other never sees it, and integration breaks in week 7 for reasons nobody can reconstruct.

04Interval algebra B owns, both depend

This lives in cvv_contracts/intervals.py rather than in B's service, because A's post-validators need it too. It is the most-tested file in the repository.

Bounds

A fuzzy date expands to the earliest and latest real date consistent with it. That is the whole trick.

def bounds(d: FuzzyDate) -> tuple[date, date]:
    if d.precision is Precision.YEAR:
        return date(d.year, 1, 1), date(d.year, 12, 31)
    if d.precision is Precision.MONTH:
        return date(d.year, d.month, 1), last_day_of(d.year, d.month)
    return date(d.year, d.month, d.day), date(d.year, d.month, d.day)

"2021" → (2021-01-01, 2021-12-31)   — a 365-day window, not a point

Three-valued overlap

class Rel(StrEnum):
    DEFINITE = "definite"   overlaps under EVERY consistent reading
    POSSIBLE = "possible"   overlaps under SOME reading
    NONE     = "none"       disjoint under every reading

def overlap(a: Interval, b: Interval) -> tuple[Rel, float]:
    a_lo, a_hi = span_bounds(a)   ((start_min,start_max),(end_min,end_max))
    b_lo, b_hi = span_bounds(b)

    pessimistic span — what is true no matter how dates resolve
    a_core = (a_lo.start_max, a_hi.end_min)
    b_core = (b_lo.start_max, b_hi.end_min)

    optimistic span — the widest either could be
    a_max  = (a_lo.start_min, a_hi.end_max)
    b_max  = (b_lo.start_min, b_hi.end_max)

    if intersect_days(a_core, b_core) > 0:
        frac = intersect_days(a_core, b_core) / min(len(a_core), len(b_core))
        return Rel.DEFINITE, frac
    if intersect_days(a_max, b_max) > 0:
        return Rel.POSSIBLE, 0.0
    return Rel.NONE, 0.0
The rule that makes the engine trustworthy

Only DEFINITE raises a scoring discrepancy. POSSIBLE is recorded and shown as context, never scored. Most Indian résumés give years only, so almost every pair of adjacent roles is POSSIBLE-overlapping — treat those as findings and the report is noise. This single decision is the difference between a system a recruiter trusts and one they turn off.

Property tests — use Hypothesis, not examples

@given(intervals(), intervals())
def test_symmetric(a, b):
    assert overlap(a, b)[0] == overlap(b, a)[0]

@given(intervals(), intervals())
def test_definite_implies_possible_span(a, b):
    if overlap(a, b)[0] is Rel.DEFINITE:
        assert intersect_days(max_span(a), max_span(b)) > 0

@given(intervals())
def test_self_overlap_is_definite(a):
    assert overlap(a, a)[0] is Rel.DEFINITE

Two contract details that prevent the classic bugs

/v1/narrate accepts only a FindingsReport. Not the document, not the ClaimGraph. If the endpoint cannot receive the source text, the narrative cannot quote something the rules never found — the guarantee is enforced by the signature, not by the prompt.

/v1/rules exists so B's catalogue is introspectable and A's fixtures can assert against it. When a rule is added, A's tests see it immediately instead of discovering it at integration.

06The extraction contract A

The single most important implementation detail in Track A: what the model returns is not the ClaimGraph.

The model never produces character offsets. Language models cannot count characters reliably, and a hallucinated offset silently corrupts every downstream provenance link. Instead the model returns verbatim text, and A recovers the offsets by searching for that text in the source. Two schemas, one boundary:

ExtractionResponse  what the model returns — structured outputs
  { claims: [ { kind, verbatim, org?, title?, degree?, issuer?,
                start_year?, start_month?, end_year?, end_month?,
                ongoing?, employment_type?, skill_refs?, stated_years? } ] }
       │
       ▼   ground_and_validate()   pure Python, no model
       │   · recover char_start/char_end by searching normalised_text
       │   · drop claims whose verbatim cannot be located
       │   · parse and validate dates, reject impossible intervals
       │   · assign stable claim_ids
       │   · attach Resolution via /v1/resolve
       ▼
ClaimGraph  what B receives

Span recovery — normalise both sides first

def recover_span(verbatim: str, source: str) -> tuple[int, int, str] | None:
    v = nfkc_collapse(verbatim)          NFKC + collapse whitespace
    s_norm, index_map = nfkc_collapse_with_map(source)

    if (i := s_norm.find(v)) != -1:
        return index_map[i], index_map[i + len(v)], "exact"

    fuzzy tier — real PDFs break exact matching constantly
    best, score = closest_window(s_norm, v)
    if score > 0.92:
        return index_map[best.start], index_map[best.end], "fuzzy"

    return None     → claim dropped, span_failures += 1
Do not skip the normalisation

Ligatures (ﬁ), non-breaking spaces, soft hyphens, and inconsistent whitespace from PDF extractors will fail naïve exact matching on a large fraction of perfectly correct claims. Without NFKC normalisation and the fuzzy tier you will watch your span-failure rate sit at 30%, conclude the model is hallucinating, and spend a week rewriting a prompt that was never the problem. Build recover_span and its test suite before the first real extraction run.

08Failure semantics

Decide these now. Every one of them is a question that will otherwise be answered differently by each person, in a hurry, in week 12.

FailureBehaviourSurfaced as
Some spans ungroundableDrop those claims, continuespan_failures > 0; degraded=true above a threshold
Document unreadableFail fast, do not guess422 unreadable_document with OCR confidence
Extraction returns zero claimsStill a valid ClaimGraphEmpty claims; every rule abstains; report says so
One rule raisesIsolate it. Other rules still runRuleOutcome(status="error", reason=…)
Rule lacks required inputAbstain — never silently passstatus="abstained" + a coverage gap entry
Narrative fails validation twiceDeterministic templatefallback_used=true
Understanding service downRetry with backoff, then fail the jobstatus="failed", webhook fired

Rule isolation is not optional

A single rule raising on an unusual claim must never take down the report. Wrap every rule.evaluate() in a try/except that records a RuleOutcome error and moves on. Without this, one malformed date in one CV produces a 500 and no report at all — and you will find that out during the demo rather than in testing.

09How the two tracks stay connected

Four mechanisms, all automated

  1. Shared package. Both services import cvv_contracts. Neither redefines a model. mypy --strict catches a drift attempt at commit time.
  2. Committed fixtures. contracts/fixtures/claimgraphs/*.json — B develops entirely against these. CI validates every fixture against the current schema, so a contract change that breaks a fixture fails the build immediately.
  3. Paired expectations. Each fixture has a matching reports/*.json. B's suite asserts fixture → expected report. This is B's regression net and it needs nothing from A.
  4. A's output test. A's suite asserts every produced ClaimGraph validates against the schema and every char_start/char_end actually indexes the verbatim it claims. That check alone catches most integration breakage before it reaches B.

Changing the contract, once implementation has started

1. Open a PR touching ONLY packages/cvv_contracts + contracts/
2. Bump schema_version   additive → 1.1.0   breaking → 2.0.0
3. Regenerate JSON Schema, update every affected fixture
4. Both people approve. No exceptions, no self-merge.
5. Merge before either service adopts the field.

After week 7 (integration checkpoint 1): additive changes only.
A breaking change means both people stop and re-plan together.
