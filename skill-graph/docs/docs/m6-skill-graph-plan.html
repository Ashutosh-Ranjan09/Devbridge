01M6 does not read the ClaimGraph

Worth settling first, because it changes what you build. The ClaimGraph is fixed, but it is not M6's input.

evidence-event.schema.json states it directly: M6 "does NOT consume discrepancies — it has no interest in fraud. It consumes corroborated capability signals, each carrying a reliability that determines how far it moves the latent-ability estimate." The single thing M6 reads is an EvidenceEventBatch.

Producing that batch is a separate job. It reads all three M5 artefacts — the ClaimGraph for what was claimed, the EvidenceBundle for what the sources returned, the FindingsReport for which claims survived — and projects them into capability events. That projection is where the interesting decisions live, and it is the piece nobody currently owns.

The gap worth naming now

Neither track in m5-work-split.html lists the event projection. Track A ends at the narrative renderer; Track B ends at the five-bucket report. Somebody has to decide that a non-fork repository with 142 commits becomes repo_artifact at strength 0.60 with skill_refs weighted typescript:0.9, nextjs:0.8, mongodb:0.6 — and that is a skill-graph judgement, not a verification one. Claiming it as part of M6 is the natural call, and it is where the modelling actually begins.

03What the documents leave open

This is the project. Everything above is settled; everything below is a decision you have to make and defend, and each one is a section of the report.

#Open questionWhy it is not a detail
O1The observation model. observation_variance = f(ρ_k, context_difficulty, sample_size) — f is never given. Nor is the map from an event to an observed ability value: how does max_rating 1495 become a number the filter can absorb?The single largest unspecified piece. Every score in the system passes through it. Expect a percentile against a reference distribution — the no-trained-models rule points straight at it.
O2Bounded scale versus unbounded Gaussian. Scores are shown in [0,1]; a Kalman update on a bounded quantity can walk outside it.Filter in logit space and transform for display, or clip and document the bias clipping introduces. Silently clipping is the wrong answer and a panel will find it.
O3Multi-skill events. One event carries several skill_refs with a relevance each. How relevance modulates the update is unstated.Every repo_artifact event is multi-skill. Folding relevance into observation variance is the obvious route, but it is a choice that needs writing down.
O4Out-of-order arrival. Events carry both occurred_at and observed_at, and a 2024 repository can be observed in 2026. Sequential Kalman updates are order-dependent.The architecture principle says scores are "recomputable from the event log at any timestamp". Recompute-on-read from a sorted log satisfies that and removes the problem; decide it before you write the ingestor, not after.
O5Propagation timing. Applied when evidence lands, or when a score is read?Write-time is fast to query but makes the graph a cache to invalidate. Read-time keeps a single source of truth and makes as_of queries natural. This is the main architectural fork in 6.3.
O6Unset constants. Prior μ₀ and σ₀² per skill; the three λ_s tiers and which skills sit in each; the h_s-to-λ_s ratio.All are sweep inputs, so they need plausible ranges as well as point values. The sweep is the deliverable — the point values are just its centre.
O7Edge types and γ disagree between documents. devbridge-plan says a single global constant per edge type, with two types. cv-to-skill-graph shows four edges with four different γ values and a third type, REQUIRES — including two REQUIRES edges at 0.70 and 0.60.Per-edge γ is a much larger parameter space to sweep and to defend. Settle on per-type before seeding the ontology, since the edges get written once.
O8Where new skills come from. L5 in the platform plan maps unseen skill strings to the ontology as an offline batch with a human approval queue — never in the request path.The only LLM anywhere near M6, and it is optional. An event naming an unknown skill_id must quarantine, not silently drop.
One published number does not reconcile — check it before you build on it

The worked /explain response reports sigma 0.12 alongside decay: { days_since_newest_evidence: 587, lambda: 0.00021 }. Under the stated σ²(t) = σ²(τ) + λ_s·Δt, the decay term alone contributes 0.00021 × 587 ≈ 0.123 to the variance, which puts σ at 0.35 or above — nearly three times the figure shown. Either λ is being applied to σ rather than σ², or its units are not per-day, or σ is capped somewhere. For σ = 0.12 to hold with σ²(τ) ≈ 0, λ would need to be about 2.5 × 10⁻⁵. Worth resolving on paper in week 1; it is exactly the sort of thing that silently defines a model.

04The five submodules

Names and boundaries follow devbridge-plan.html §03. Build them in this order — each one is testable on its own.

ontology-service

6.1

The skill vocabulary and the edges evidence propagates along. Must land first: skill_id is the join key on every incoming event, so nothing binds until it exists.

  • Skill nodes seeded from ESCO, plus a reviewed alias table
  • Edge types and γ per type — settle O7 here
  • Language versus framework distinction (claim shape 11: Next.js and NumPy resolve to framework nodes, not language nodes)
  • Quarantine path for unknown skill ids

evidence-ingestor

6.2

Validates, authorises and persists. Contains no modelling at all, which is what makes it finishable in days rather than weeks.

  • Schema validation against the committed JSON Schema
  • Idempotent on event_id — replay must be safe
  • consent_scope check; refuse what is not covered
  • Immutable evidence nodes, indexed by occurred_at
  • Record refusals rather than dropping them

scoring-engine

6.3

The technical core and the part a panel interrogates hardest. Everything in §03 that is still open lands here.

  • Observation model — event to (observed, variance)
  • Kalman update, in whichever space O2 resolves to
  • Decay kernel over elapsed time
  • Propagation across ontology edges
  • Deterministic recompute from the event log

query-api

6.4

The surface everything else reads. Its response shape is already fixed by the worked example, so build to that exactly.

  • GET /v1/developers/{id}/skills
  • GET …/skills/{skill}/explain — contributions, decay, abstentions
  • as_of parameter for historical state
  • Health, readiness, metrics, OpenAPI — the house convention

integrity-analytics

6.5

Adversarial defence. Genuinely valuable and genuinely optional — cut this before cutting the validation work in §06.

  • Commit-farming detection: many trivial commits
  • Anomaly detection on evidence-arrival patterns
  • Author date versus committer date versus push timestamp
  • Community detection is platform-scope, not M6-alone

event projection

new

The unowned piece from §01. Small in code, large in consequence — it decides what the model ever sees.

  • ClaimGraph + EvidenceBundle + FindingsReport in, batch out
  • Kind selection and skill_refs relevance weighting
  • Reliability factors applied and named
  • not_emitted[] populated with a reason every time

05The example is a calibration target

The repository already contains one CV traced end to end, with per-skill scores at the far end. That is unusually useful: the free constants in §03 can be chosen so the pipeline reproduces it.

Treat these as targets, not ground truth

They come from a design document, not from a running implementation, and the document says so itself — the reliability constants are "documented priors, swept in the sensitivity analysis, not fitted." Use them to sanity-check that your parameter choices land in the right region and preserve the right ordering. Do not tune constants until the numbers match exactly; that would be fitting to a single fabricated example, which is worse than not matching.

The ordering is the part that must survive. numpy below python below typescript below cpp, and python depressed relative to its raw evidence purely by staleness — if a parameter sweep breaks that ordering, the sweep has found a real problem.

06Decay is the mechanism to get right

It is the platform proposal's stated differentiator, the easiest thing to implement wrongly, and the clearest single figure in a viva.

07Validation is the deliverable

A skill graph that produces plausible numbers is a demo. The three experiments below are what make it a project, and none of them needs a real user or a trained model.

ExperimentConstructionThe claim it settles
Parameter recoveryGenerate synthetic developers with known true ability. Simulate evidence arriving from sources of known reliability, at irregular intervals. Run the filter.That the model works at all. Ground truth is exact because you set it. Build the generator first — it is also your test corpus for everything else.
Sensitivity sweepSweep ρ_k, λ_s, h_s and γ across their full plausible ranges. Report Spearman rank correlation of candidate orderings against the centre-point run.That the unfitted constants do not secretly determine the answer. "Rank correlation above 0.9 across the entire space" is stronger than any fitted value without a confidence interval.
Per-source ablationRemove each evidence stream in turn — platform, repository, CV claim, deployment — and re-run. Immutable evidence nodes make this a filter over the log, not a re-collection.The central multi-source thesis. The worked example predicts the shape of the answer: dropping platform evidence should gut cpp while leaving typescript intact, and dropping repositories should do the reverse.
The property that makes all three cheap

Scores are recomputable from the immutable event log at any timestamp. That one architectural commitment turns ablation into a log filter, turns the sweep into a loop over parameter sets, and turns as_of queries into a free feature. If O4 and O5 are resolved toward recompute-from-log, this section costs days instead of weeks — which is the strongest practical argument for resolving them that way.
