# Assessment — build plan

**DevBridge, the assessment layer.** A recruiter gives a job description; the module
extracts the skills it requires, a person confirms them, the skill graph (M6) surfaces
candidates who clear the must-haves, and each chosen candidate gets a coding task that
is unique to them and exactly as hard as everyone else's. Their code runs in a sandbox,
is scored by tests alone, and the result goes back into the skill graph as evidence.

> Like the other two modules: **no overall score, no verdict.** The module reports what
> was tested and what happened. A person decides what it means.

---

## 1. The flow

```
JD text ──1──▶ extract skills (LLM, closed choice, every skill quoted from the JD)
        ──2──▶ must / nice proposed ──3──▶ recruiter edits and CONFIRMS
                                                │  requirements.json  (schemas/job-requirements)
                                                ▼
        ──4──▶ M6 shortlist: every must-have clears its bar; nice-to-haves shown; no ranking
                                                │  recruiter picks candidates
                                                ▼
        ──5──▶ pattern per must-have skill (lookup by skill id)
        ──6──▶ variant per candidate: parameters chosen (seed, or LLM from the ALLOWED values),
               requirements rendered by code, story by LLM, tests generated by code and
               checked against the reference solution and the mutants before anyone sees them
        ──7──▶ sandbox run (Docker, no network) ─▶ score by tests ─▶ report
               ─▶ assessment_result event ─▶ M6 ingests it like any other evidence
```

| Step | Owner | Model? |
|---|---|---|
| 1–3 JD intake and confirmation | `assessment` | LLM proposes; code checks; a person confirms |
| 4 Shortlist | `skill-graph` (M6) | none |
| 5 Pattern selection | `assessment` | none |
| 6 Variant generation | `assessment` | LLM chooses among allowed values and writes the story; code does the rest |
| 7 Run, score, report, feed | `assessment` → M6 | none |

## 2. Principles — each from a failure we have already seen

1. **The model chooses; it never invents anything that is scored.** Skills come from the
   shared list, parameter values from the pattern's allowed values, and every hidden
   test from code. A free-form generated constraint makes candidates' tasks unequal,
   and a generated test fails a candidate for the test's own mistake.
2. **Every variant is validated before a candidate sees it.** Its hidden tests must pass
   the pattern's reference solution and each mutant must fail at least one. A suite a
   mutant passes is too weak; a suite the reference fails is wrong.
3. **Equal difficulty is a property of the pattern, not a hope.** Parameters vary
   surface and numbers; exactly one twist per variant, and every twist in a pattern
   carries the same rating. Calibration watches for a twist that turns out harder.
4. **A run that could not happen is not a score.** Sandbox failures are typed outcomes;
   only outcomes the candidate caused are scored.
5. **Grounded extraction.** Every skill taken from a JD carries the JD's own words. A
   quote not in the JD drops the skill — the same rule as M5's span grounding.
6. **Unknown is reported, never dropped.** A JD skill not on the list, or a must-have
   with no pattern, is listed as such.
7. **Honest about cheating.** Unique variants stop copying from another candidate. They
   do not stop help from an AI assistant; the time limit narrows it, nothing removes it.

## 4. A pattern

```yaml
id: rate_limiter
version: 1
skill: rate_limiting            # an id in schemas/skills/ontology.yaml — checked on load
title: Rate-limiting middleware
level: medium                   # easy | medium | hard
time_limit_minutes: 40
language: python
core: Allow at most LIMIT requests per KEY in a sliding WINDOW; reject the rest.
parameters:                     # every value in a list is equally hard
  key_kind: [ip_address, api_key, user_email]
  limit: [3, 5, 10, 15]
  window: [60, 900, 3600]
twists:                         # exactly ONE per variant; ratings must all be equal
  retry_after:   {rating: 1, rule: …}
  remaining:     {rating: 1, rule: …}
  error_payload: {rating: 1, rule: …}
tests:                          # named groups; reports and calibration use these names
  core: [allows_up_to_limit, rejects_one_over, keys_independent, window_slides, exact_boundary]
  twist: [twist_behaviour]
```

- `starter.py` — the interface the candidate fills in. The tests call only this.
- `requirements.md` — the requirements text with `{placeholders}`. **Rendered by code**,
  so the numbers a candidate is graded against are exactly the numbers they were given.
- `story.md` — the fallback scenario paragraph, used when no model is available.
- `tests_hidden.py` — one pytest file that reads `params.json`. The only scorer.
- `reference.py` — a correct solution, written by a person.
- `mutants/*.py` — deliberately wrong solutions the tests must catch.

**`assess validate PATTERN`** runs the hidden tests over **every** parameter combination
(108 for rate_limiter) against the reference and each mutant. A pattern ships only when
the reference passes all of them and every mutant fails in every combination.

## 5. A variant

`generate(pattern, seed, *, context=None, provider=None, avoid=())`:

1. **Parameters.** From the seed by default. With a JD (`context`) and a model, the
   model *chooses* a value for each parameter and the twist, from the allowed lists
   only; any choice off the list is replaced by the seeded one, and the variant records
   which was used (`chosen_by`).
2. **Uniqueness within a job.** If the parameters equal a variant already issued for
   the same job, the next seed is tried (bounded), so two candidates for one role never
   receive the same task.
3. **Requirements** rendered from `requirements.md` by code.
4. **Story.** The model writes the scenario paragraph from the parameters and the JD.
   Guard: every number in the story must be one of the variant's parameter values, or
   the story is discarded for the template. No model, or any failure: template story.
5. **Validation.** Not per variant, as first planned: the pattern is validated over EVERY
   combination before any variant is issued (see the build record).
6. **`variant_id`** = `v_` + sha256(pattern id, version, parameters)[:12].

The candidate receives: story, requirements, starter, time limit. Hidden tests,
reference and mutants never leave the server.

## 6. Sandbox and outcomes

Candidate code runs only in Docker:

```
docker run --rm --network none --read-only --tmpfs /tmp:rw,size=16m
  --memory 256m --cpus 0.5 --pids-limit 64 --user 10001
  -v <dir>:/work:ro  assess-python:3.12
  pytest -q -p no:cacheprovider --timeout=2 --junitxml=/tmp/out.xml /work/tests_hidden.py
```

Per-test timeout (2 s) means one infinite loop fails one test, not the run. A wall-clock
limit (30 s) bounds the whole container.

| Outcome | Cause | Scored? |
|---|---|---|
| `passed` | every test passed | yes |
| `tests_failed` | some tests failed | yes |
| `import_error` | the solution does not import — a syntax error, or it raised while importing (e.g. reaching for the network) | yes — 0 |
| `timeout` | the whole run exceeded the wall clock | yes — 0 |
| `resource_limit` | killed for memory (exit 137) | yes — 0 |
| `sandbox_unavailable` | Docker missing, image missing, daemon error | **no** — retry |

Trusted code (reference, mutants) is validated locally with the same test file, without
Docker, so validation works on a machine with no daemon.

## 7. Scoring and the report

Score = hidden tests passed / total, split into `core` and `twist`; time used from
session start to submission. A submission after the deadline plus 2 minutes' grace is
refused, not scored. The report names every test, whether it passed, and why not. No
pass/fail field, no grade.

## 8. Sessions and storage

SQLite at `assessment/.data/assess.db` (gitignored). Tables: `jobs`, `variants`,
`sessions`, `results`. A result is written once and never updated. A session is
`issued` → `open` → `submitted`, or `expired`. One session per (candidate, pattern, job).

A job's task is `issued` with no clock and a start-by date the recruiter chose (7 days
by default, at most 60); its story, requirements and starter are withheld until the
candidate presses Start, which sets `started_at` and the deadline. The first version
started the clock when the task was issued, so a candidate lost the minutes between a
recruiter pressing Send and opening the page, and could find a task expired unseen.
Practice is issued and begun in one step. Expiry is decided whenever a session is read,
not only when a late submission arrives: before, an abandoned task said `open` forever.

**Run and attempts.** Run executes `tests_visible.py`, a few examples read straight off
the requirements, in the same sandbox: unlimited while the task is open, shown with
their details, stored nowhere. Submit runs the hidden tests and is one of three
attempts, each stored in `attempts` with its code. The last attempt counts; the session
is final, and its result written to `results`, at the third attempt, at one passing every
test, at Finish, or at the deadline (with no attempt, `expired`). Code that does not
parse is refused before either, by `compile()`, and costs nothing. The first version gave
one submission: a candidate whose paste was cut off mid-line lost the task to a
SyntaxError. The recruiter reads every attempt; M6 hears only the counted one.

## 9. The JD layer

**Extraction** — one model call: the JD text and the shared skill list (ids and labels).
The model returns, per skill: the id or null, the JD's own words for it (`quote`), and
`must` or `nice`. Code then:

- drops an item whose `quote` is not in the JD (whitespace- and case-normalised);
- keeps an id only if it is on the list, else records the surface name as
  "not on the skill list";
- coerces an unknown priority to `nice` and marks it `needs_review`;
- deduplicates by id; marks each skill `assessable` if a pattern exists for it.

No model, or a failed call: a rule-based fallback finds skill ids and aliases as whole
words in the JD, quotes the sentence, and proposes `nice` — every item `needs_review`.

**Confirmation** — the recruiter may change priorities, drop skills, add skills from the
list, and set a **bar** (0–1) per must-have. `confirm` locks the job: a confirmed job is
never edited, only superseded by a new one.

**Export** — `assess jd export JOB` writes `requirements.json` against
`schemas/job-requirements.schema.json`: must-haves with bars, nice-to-haves.

## 10. The shortlist (M6)

`python -m m6_query shortlist --requirements requirements.json`:

- a candidate qualifies when **every** must-have clears its bar — the interval's lower
  bound by default (`definite`), as M6's search already decides for one skill;
- the output lists qualifying candidates with every must-have and nice-to-have interval;
- **alphabetical, no ranking.** Combining several skills into one order needs a weighted
  sum, which is the overall score both modules refuse. The recruiter reads the columns.

Also `POST /shortlist` on M6's combined server, with the same JSON. A must-have needs
DIRECT evidence — an interval inferred from a neighbouring skill is a hint, not a
demonstration. The requirements are checked against the schema on arrival.

## 11. Feeding results back (M6)

`assess events SESSION` writes an `EvidenceEventBatch` with one `assessment_result` event:
the pattern's skill at relevance 1.0, `occurred_at` = submission time, payload: pattern,
version, variant, level, passed, total, outcome. `subject_ref` is the candidate reference
the session was started with — the same M6 subject.

M6 changes, as its own CLAUDE.md anticipated: `assessment_result` in the event schema's
`kind` enum, `source.module` accepts `assessment`, priors and an observed-value rule in
`m6-parameters.yaml`:

```
observed = floor + (ceiling[level] − floor) × passed / total
floor 0.20 · ceiling: easy 0.80 · medium 0.86 · hard 0.92   (parameters 1.1.0)
strength 0.75 · reliability_base 0.85      (observed under a time limit; help not ruled out)
```

Each ceiling sits just above the most a Codeforces peak in the matching band observes
under M6's measured rating table: easy above a Pupil, medium above a Specialist, hard
above any rating. They were 0.65 · 0.78 · 0.88, set against the approximated table, under
which a 1495 peak observed 0.739; measured, it observes 0.834 and outranked a fully passed
medium task.

Only scored outcomes produce an event. `sandbox_unavailable` produces none.

## 12. Calibration

`assess calibrate PATTERN` over all results for one pattern **version**: pass rate per
named test, per twist; a twist whose pass rate differs from the others' mean by more
than 20 points, with at least 15 attempts each, is flagged. It reports; re-rating is a
person's edit to the pattern, which bumps its version. Versions are never mixed.

## 14. What this module does not do

Filter or reject candidates · produce an overall score · grade style or code quality ·
stop a candidate using an AI assistant · invent a constraint or a test.

## Build record — where the build differs from the design, and why

| Design said | Built | Why |
|---|---|---|
| validate each variant before issuing it | validate the PATTERN over every combination, cached by a hash of its files | every variant is one of those combinations, so this is stronger and instant per candidate; any file edit forces re-validation |
| outcome `syntax_error` | `import_error` | a solution that reaches for the network fails at import, not on syntax; the outcome is "does not import" |
| priors for the event in M6's parameters | trust in `assessment/contracts/evidence.yaml`, worth in M6's `observed_value.assessment_result` | the emitter states how far to trust a result; the graph decides what it is worth — the boundary the projection already keeps |
| `POST /shortlist` on M6's query API | on M6's combined server | the query API serves GET only; the combined server already takes request bodies |
| — | a must-have needs direct evidence in the shortlist | `c` reached a candidate only by propagation from `cpp`; that is not a demonstration |
| settings from `.env` | from `assessment/.env`, wherever the command runs | a working-directory-relative `.env` loaded nothing from elsewhere, and the model step fell back silently — the CLI now also warns when the model was asked but not used |
| whole-word skill matching | hyphens join words | "go" was found in "go-getter" |
| rules propose the first mention of a skill | the most demanding mention | "Build services in Python" then "Strong Python is required" is a must-have |
| validation's per-test limit 5 s | 2 s, the sandbox's own (`sandbox.PER_TEST_SECONDS`) | validation runs on the full CPU; a trusted solution needing more than 2 s there fails in the sandbox anyway. It also halves the DSA pattern's validation, where the quadratic mutant times out in every combination |
| test ids per pattern | `validation._case_id` builds them from the pattern's own parameters | it had rate_limiter's three parameter names written in; the second pattern was the first to need anything else |
| twists as alternative rules | twists as extra functions in the DSA pattern | one reference implements every twist; two tie orders contradict, so the tie order is fixed in the core |
| an HTTP API, later | `assess serve`: the CLI's commands as endpoints, no rule of its own | the web layer needs one; keeping every rule in the functions it calls means CLI and API cannot disagree |
| — | a result has two views: candidate (test names, passed) and full (with each failure's detail) | the detail quotes the hidden test's input and expected answer; a candidate who saw it could fit a retry to the tests |
| — | a new store per HTTP request | FastAPI runs sync handlers on a thread pool; an sqlite3 connection refuses use from another thread |
| — | a bar must be within 0–1, checked in `jd.edit` (and in the API's body) | `jd.edit` uses `model_copy`, which does not re-validate: `--must x:5` stored 5.0 |
| — | a sandbox failure's note is Docker's reason | the note kept Docker's last stderr line, its usage hint, instead of the line before it ("No such image: …") |

Measured on the reference pattern: 108 combinations, 648 cases, the reference passes all,
8 mutants each caught in every combination it applies to, in 7 s. In the sandbox: the
reference 6/6, the fixed-window mutant 5/6 failing exactly `exact_boundary`, a syntax
error and a network call both `import_error`, an infinite loop 0/6 by per-test timeouts,
a 1 GB allocation `resource_limit`.

The second pattern, `top_k_frequent` (DSA, skill `algorithms`): 27 combinations, 216
cases, the reference passes all, 11 mutants each caught in every combination, in 83 s
— 81 s of it the quadratic mutant timing out once per combination, so that run is
`-m slow` and the default suite validates one combination per twist (12 s). In the
sandbox the reference passes 8/8 in under a second, the large input included; the
quadratic mutant fails exactly `large_input`. A result fed to M6 gave `algorithms
[0.665, 0.809]`.

Over HTTP (29 October), with real servers: a JD by rules, `rate_limiting` added as a
must-have, confirmed; one task issued (`python`, `sql` reported not assessable); the
reference submitted through Docker, 6/6; a second submission 409; the events batch
accepted by M6's `POST /evidence/batch`, giving `rate_limiting [0.665, 0.809]`; M6's
shortlist on the exported requirements: 0 qualified, since nothing yet evidences
`python` or `sql`. With an image that does not exist: `/healthz` degraded, submit 503
("No such image: …"), the session still open, no result.
