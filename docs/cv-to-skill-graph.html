Two extraction details this example exercises

The GitHub handle is derived, not stated. This CV never prints a profile URL — only repository URLs. The owner segment must be parsed out of the path, and the resulting claim carries derived_from_repo_url so a reviewer knows it was inferred. Miss this and eighteen downstream checks silently never run.

The declaration marker is a claim, not metadata. Modelling the institution's own disclaimer as a first-class claim lets the rules read it. Coursework claims inherit unverified from it rather than being separately assessed and confidently reported on.

The one contradiction, and why it is not an accusation

A dead deployment link is a fact — the URL returns 404. It is not evidence of dishonesty: free hosting expires, projects get taken down, subdomains get reclaimed. The report states what was found and leaves the meaning to a person. Precisely the decisive-but-not-automatic case.

05Becoming skill-graph evidence

M6 does not consume discrepancies — it has no interest in fraud. It consumes corroborated capability signals, each carrying a reliability that determines how far it moves the estimate.

Unverified ownership caps reliability at ingest

This bundle carries ownership: "claimed_unverified". Every GitHub-derived event is therefore emitted with reliability multiplied by 0.6 — and events that would raise a score are capped, while contradicting events are not. The asymmetry is deliberate: nobody lists a handle that undermines them, so a contradiction from a self-claimed account is credible in a way corroboration is not.

Read the two extremes — this is the multi-source thesis in one candidate

C++ scores well with no repository evidence at all. Competitive programming does not live in GitHub. Its entire signal comes from one Codeforces API call at reliability 0.90. A repository-only system would have scored this candidate's strongest skill near zero.

TypeScript scores well with no platform evidence at all. 335 KB of shipped TypeScript across two substantial non-fork repositories, plus a live deployment. A contest-only system would have missed it entirely.

Neither source covers both. That is the whole argument for fusion, and this single CV demonstrates it — which is why it belongs in the report.

Decay in action

Python's evidence is a single repository last touched June 2024 — 26 months before the reference date. Under σ²(t) = σ²(τ) + λ_s·Δt the uncertainty has grown wide, so the lower bound sits at 0.29 while the mean is materially higher. The score has not fallen because the candidate got worse; it has fallen because we know less. One fresh Python commit restores it immediately — no points to re-earn.

Contrast TypeScript, whose newest evidence is June 2025: a narrower band and a higher bound from comparable raw strength.

What M6 refuses from this bundle

  • Employment and education discrepancies — not capability signals; they stay in the verification report.
  • Advisory findings (D11, D12) — non-scoring by construction; the aggregator cannot pass them on.
  • The 404 deployment — a dead link says nothing about skill. It is a report finding, not evidence.
  • CGPA, coursework, JEE rank — the institution disclaimed them and no skill maps to them.
  • Anything at unverified-ownership reliability that would raise a score — capped at ingest, before the filter sees it.

Each evidence node is immutable and referenced by every score it touched, so any number decomposes on demand.

Three properties fall out of this and all three matter under questioning. A recruiter can see exactly why a number is what it is. A candidate can see what the system used and contest a specific node. And the evaluation harness can ablate any single source and re-run, which is what makes the fusion claim in §05 measurable rather than asserted.
