01The technical thesis

The proposal describes a business. A B.Tech project needs a defensible technical claim underneath it — something a panel can ask you to prove, and something you can measure.

The claim worth building the project on:

Central claim

Developer competence can be estimated from heterogeneous, partially unreliable behavioural evidence — commit history, sandboxed performance, delivery outcomes, document claims — by fusing it into a single calibrated latent-ability model with explicit uncertainty that grows over time. The fused estimate outperforms any individual evidence stream, and its stated confidence is empirically accurate.

That claim decomposes into three contributions you can defend independently, each with its own experiment:

ContributionWhat is genuinely hardHow it is proven
Multi-source evidence fusionSources disagree, arrive irregularly, and have different reliabilities that nobody has measuredAblation study per evidence stream; parameter-recovery simulation against known ground truth; sensitivity sweep showing ranking stability
Temporal consistency verificationProving a CV claim false requires reconciling free-text claims against behavioural traces on a timelineInjected-falsification corpus with perfect ground truth; per-fraud-type detection rate at fixed FPR
Authorship & origin consistencyDeciding whether a code sample is consistent with an author’s own established style, without a labelled fraud corpus to learn fromSeparation between self-distances and the empirical null; ROC over the reference corpus; robustness under auto-formatting

Everything else in the proposal — the marketplace, escrow, factoring, the recruiter console — is competent engineering that supports the claim but does not constitute it. Build it, scope it honestly, and do not let it consume the semester.

Framing note

The system must never output a hiring verdict. It outputs calibrated evidence with stated uncertainty, and routes conflict to a human. This is both the ethically correct design and the one that survives a viva — "what happens when you're wrong about someone?" has a good answer only in this framing.

02Architectural principles

Seven rules that the module boundaries, the contracts, and the review checklist all derive from. Every later section is an application of these.

1 — Contracts before code

Each module publishes an OpenAPI 3.1 document into a shared /contracts directory before its implementation begins. Clients are code-generated from those documents, never hand-written. A module is "done" when it satisfies its contract tests, not when its UI works. This is what actually makes independent parallel work possible across a team.

2 — No shared database

Every module owns its storage exclusively. Cross-module reads happen over HTTP; cross-module writes happen over events. The moment two services share a table, the module boundary is decorative and the project becomes a monolith with extra latency.

3 — Evidence is append-only

Nothing overwrites an evidence record. Scores are derived and recomputable from the event log at any timestamp. This buys you three things a panel will notice: time-travel debugging, reproducible experiments, and a clean answer to "delete my data" that does not corrupt every score in the system.

4 — The LLM boundary

The rule that governs every model call

An LLM may translate unstructured → structured, or structured → human prose. It may never produce a number that enters a score, and it may never be the thing that decides whether a claim is true. Judgement is deterministic, auditable, and re-runnable; language handling is not.

Concretely this means claim extraction is a model call, and consistency checking is a rule engine. Challenge generation is a model call, and challenge validation is program execution. Report prose is a model call, and every number in that prose was computed elsewhere. Section 08 registers every call site individually.

5 — No trained models

A hard constraint, adopted deliberately

Nothing in this system is a trained model. Every quantitative judgement comes from descriptive statistics against a reference distribution — distances, percentiles, empirical nulls, closed-form filter updates. There is no optimiser, no labelled training set, no learned weights anywhere in the pipeline.

This began as a resource constraint and turned out to be the better design. A trained classifier that says someone’s code is inconsistent with their history is a black box making an accusation. A percentile against an explicit reference distribution decomposes into exactly which features deviated and by how much — which is the only form in which such a claim should ever be shown to the person it is about. It also removes the project’s single largest data dependency: labelled examples of the thing you are trying to detect, which nobody has.

Note that the Bayesian filter in §06 is not a trained model. Kalman updates are closed-form equations applied in a loop; the parameters that govern them are set from documented reasoning and stress-tested by sensitivity analysis (§06), not fitted.

6 — Confidence, never verdicts

Every module emits (value, confidence, evidence_refs). No module emits a boolean pass/fail. Aggregation happens once, in the skill graph, under a documented model — not implicitly by whichever service happened to threshold first.

7 — Standalone-first for the verification engine

The CV Verification Engine is built as a product with external customers from day one: its own auth, its own metering, its own OpenAPI surface, zero imports from marketplace code. It must run correctly on a CV from someone who has never touched the platform. Everything the marketplace needs from it, it gets through the same public API an enterprise would use.

The claim model

Every extracted claim is an interval-typed assertion with provenance back to a character range in the source document. Span grounding is enforced, not trusted: if the returned span does not literally appear in the source text, the claim is rejected and re-extracted. This is the single most effective guard against fabricated extractions.

Claim {
  claim_id, subject_id, kind: employment | education | certification | project | skill,
  interval: { start: YYYY-MM, end: YYYY-MM | present, precision },
  attributes: { org?, title?, degree?, issuer?, skill_refs[] },
  provenance: { doc_id, char_start, char_end, verbatim },
  resolution: { canonical_org_id?, canonical_title_id?, confidence }
}

Consistency rules — the deterministic core

Each rule emits Discrepancy(type, severity, confidence, evidence_refs). None emits a verdict. The interesting rules are the cross-modal ones — claims checked against behaviour rather than against other claims.

RuleChecksSignal quality
Interval conflictTwo full-time employments overlapping, or full-time study overlapping full-time workStrong, low FPR
Commit-activity reconciliationClaimed employment period against observed commit cadence, timezone histogram, and organisational repository accessStrong when public activity exists; abstains otherwise
Skill-tenure plausibilityClaimed years of a technology against earliest observed evidence of it, and against the technology's release dateVery strong — a claim predating the technology is decisive
Title progressionSeniority trajectory against tenure lengths, using a canonical title ladderWeak, advisory only

Deliberate design constraint

Gap detection and title-progression rules are the two most likely to encode bias against people with non-linear careers — caregiving, illness, non-Western career ladders. They stay in the system as advisory, non-scoring, human-visible flags. Section 13 makes measuring that bias an explicit deliverable rather than a disclaimer.

05M3 — Code Provenance Engine

The module that answers three separate questions people conflate: did this person write this code, is this code original, and what does it demonstrate they can do.

5.1 Repository analysis

One parser front-end for every language: tree-sitter gives real ASTs across Python, JavaScript, TypeScript, Java, Go, C++, Rust and more from a single integration, which is what makes multi-language analysis tractable for a student team. From the AST: cyclomatic and cognitive complexity, function length distributions, test-to-source ratio, dependency profile, framework fingerprints, error-handling density.

5.2 Authorship verification

Formulated as open-set verification, not closed-set attribution. The question is never "which of these 50 people wrote this" — it is "is this sample consistent with the profile claimed by this account," answered with a calibrated probability.

Feature familyExamplesRobustness
Syntactic (AST)Node-type unigram/bigram distributions, AST depth profile, node-type TF-IDFHigh — survives reformatting
IdiomaticLoop construct preference, comprehension vs. imperative, exception-handling style, import organisationHigh
LexicalIdentifier casing ratios, identifier length distribution, abbreviation habits, comment density and registerMedium
LayoutIndentation, brace placement, blank-line rhythm, line-length distributionLow — destroyed by formatters
Repository metadataCommit hour-of-day histogram (a timezone fingerprint), weekday pattern, commit size distribution, message styleMedium — and hard to fake unintentionally

Method — a one-sample test, not a classifier

The question is answered by distance against an empirical null, with no model fitted at any point:

  1. Profile. From the author’s established history, compute the feature vector’s per-feature mean and variance. This is their style profile — descriptive statistics over their own work, nothing more.
  2. Measure. For a new sample, compute Mahalanobis distance to that profile, so features the author is personally consistent about count for more than features they vary anyway.
  3. Reference. Compute, once, the distribution of distances between known different-author pairs drawn from the Google Code Jam corpus. This is the empirical null — a lookup table built by a for-loop, not a training run.
  4. Report. Place the observed distance as a percentile of that null. The output is “this sample sits at the 3rd percentile of consistency for this author,” which is calibrated by construction.
Why this beats a classifier here

It measures self-consistency rather than predicting a label, so it needs no examples of the thing being detected — and no such labelled corpus exists to be had. It is also fully decomposable: any flagged sample breaks down into which specific features deviated and by how much, which is the only defensible way to show such a finding to the person it concerns. And it degrades honestly: an author with too little history yields a wide profile and the test abstains, rather than guessing.

The experiment worth running

Auto-formatters (black, prettier, gofmt) are now near-universal, and every layout feature in the classic stylometry literature dies under them. Pass the reference corpus through each formatter, recompute the null, and measure how much separation each feature family retains. Showing that AST-family features survive what kills layout features is a genuine finding, needs no training, and is entirely within reach of a semester.

5.3 Model-generated code detection

This did not exist as a problem when the stylometry literature was written, which is exactly why it is worth your attention. Handled entirely by deterministic rules over commit history — the stronger signal family in any case, and the one that needs no model:

  • Process-level rules — large complete commits arriving with no iterative refinement, absent debugging commits, tests added wholesale rather than incrementally, no intermediate broken states. Human development leaves a characteristic mess in the history; generated code often arrives finished.
  • Artefact-level thresholded statistic — stylistic uniformity and comment-to-code ratio measured against the same empirical null used for authorship. Optionally, perplexity under a pretrained code language model, used at inference only.

Treated as one signal among many, never as an accusation. The honest framing is “this repository shows little evidence of iterative authorship” — which is both defensible and, being a statement about the commit graph rather than about a person, checkable by anyone.

5.4 Originality

Winnowing-based fingerprinting (the MOSS approach) against a corpus of tutorials, boilerplate, popular starter templates, and vendored dependencies. The dominant real-world case is not plagiarism — it is node_modules, generated code, and framework scaffolding inflating someone's apparent output. Detecting and excluding it is what makes the volume metrics meaningful at all.

06M6 — Skill graph & the scoring model

The technical core, and the part a panel will interrogate hardest. It deserves a real model, not a weighted sum with hand-picked constants.

Formulation

For each (developer, skill) pair, maintain a latent ability with explicit uncertainty — a Gaussian state (μ, σ²) updated by Bayesian filtering as evidence arrives. Each evidence event carries a source-specific reliability ρ_k that determines how much the observation moves the estimate. The update is closed-form: no fitting, no optimiser, no training data — the equations below are applied directly.

on evidence e from source k at time τ:
   observation_variance = f(ρ_k, context_difficulty, sample_size)
   (μ, σ²) ← kalman_update((μ, σ²), observed, observation_variance)

between events, over elapsed time Δt:
   σ²(t) = σ²(τ) + λ_s · Δt          uncertainty grows
   μ(t)  = μ(τ) + (prior_μ − μ(τ)) · (1 − e^(−Δt / h_s))

displayed score:
   score = μ − z·σ                    a lower confidence bound
Why decay is modelled as growing uncertainty, not a falling score

The proposal says scores decay. Implementing that as "subtract points over time" asserts something false — that the person got worse. Modelling it as growing variance asserts something true: we know less than we did. Because the displayed number is a lower confidence bound μ − zσ, a stale profile still falls — but for a defensible reason, and it recovers immediately on fresh evidence rather than needing to re-earn points. This reframing costs nothing and is a much stronger answer under questioning.

Parameters — chosen from reasoning, stress-tested by sensitivity analysis

ParamMeaningHow it is estimated
ρ_kReliability of evidence source kOrdered from first principles — an executed test is more reliable than a client star rating — then swept across its plausible range.
λ_sVolatility of skill sSet per skill class from ecosystem release cadence: a framework decays faster than a fundamental. Three tiers, not a continuum.
h_sMean-reversion half-lifeTied to λ_s by a fixed ratio rather than set independently, to keep the parameter count small enough to sweep exhaustively.
γ_edgePropagation damping across ontology edgesSingle global constant by edge type (prerequisite vs. related). Evidence for React partially informs JavaScript.
Sensitivity analysis replaces parameter fitting — and is the stronger result

Fitting these would need outcome labels at a volume no student project will have; fitting them on thin data produces overfitted constants dressed up as science. Instead: set each from documented reasoning, then sweep the full plausible range and report how stable candidate rankings are across it. “Rank correlation stays above 0.9 across the entire plausible parameter space” is a stronger claim than a fitted value with no confidence interval, and it is the honest thing to say given the data available.

Pair it with a parameter-recovery simulation: generate synthetic developers with known true ability, simulate evidence arriving from sources of known reliability, and confirm the filter converges to the truth. This validates the model end to end, requires no real users, and involves no training — it is simulation plus arithmetic.

Graph structure

A property graph (Neo4j, or Postgres with recursive CTEs if you want one less system to operate): Skill nodes with PREREQUISITE_OF and RELATED_TO edges, seeded from ESCO/O*NET and extended with a reviewed alias table. Developer nodes hold per-skill states; Evidence nodes are immutable and referenced by every score, which is what makes any score explainable on demand.

6.5 Anti-gaming

A scored marketplace is an adversarial environment; treat it as one from the start. Detection targets: Sybil clusters posting gigs to each other, review-reciprocity rings, commit-farming (many trivial commits), backdated history via rewritten git timestamps, assessment collusion (near-identical solutions across accounts, timing correlation). Techniques: graph community detection on the transaction graph, statistical anomaly detection on evidence-arrival patterns, and cross-checking git author dates against committer dates and push timestamps — the latter is a cheap, decisive check that most systems skip.

07M4 — Assessment engine & sandbox

Isolation

You are executing untrusted code submitted by strangers. Recommendation: gVisor (runsc) under containerd — user-space syscall interception gives strong isolation without the operational weight of managing microVMs, and it runs on ordinary hardware. Firecracker is the documented upgrade path if you want a stronger boundary and have KVM available.

Threat model to write up explicitly, because a panel will ask: network egress (block all, including DNS — DNS exfiltration is the one people forget), filesystem escape, resource exhaustion via CPU/memory/PID/disk quotas, fork bombs, cryptomining, and side-channel timing attacks against other tenants. Each gets a control and a test that attempts the attack.

Determinism

Scores must be reproducible: base images pinned by digest, fixed random seeds, no network, CPU pinning where timing contributes to the score, and a fixed wall-clock budget enforced outside the sandbox rather than inside it.

Challenge synthesis and its validation loop

Generating novel, role-specific problems is the one place in this system where an LLM is doing something no other technique can. But a generated challenge is worthless until it is proven to work — so generation is wrapped in an execution gate:

  1. Generate spec, statement, starter code, reference solution, hidden test suite, and rubric from a target skill vector and difficulty. LLM · L4
  2. Execute the reference solution against the hidden tests. It must pass completely, or the challenge is discarded.
  3. Execute deliberately mutated/incorrect solutions. They must fail, or the tests are not discriminative and the challenge is discarded.
  4. Pilot on a cohort; compute empirical difficulty (raw pass rate) and discrimination (point-biserial correlation between item score and total score). Two formulas, no model fitted.
  5. Admit to the registry only on passing all four. deterministic gate
Why this is the right shape

Nothing generated is trusted on the strength of having been generated. The model proposes; execution disposes. "First-pass validation rate" then becomes a real metric you can report, and difficulty drift becomes measurable rather than assumed.

Scoring

Three independent components, reported separately rather than collapsed into one number too early: functional correctness (hidden test pass rate, weighted by test importance), code quality (the same static analysis M3 runs, so a candidate is measured the same way in both contexts), and process signals from the edit trace.

Comparability across different challenges comes from percentile scoring against the cohort distribution for that item, not from a latent-trait model. A raw score becomes “72nd percentile among candidates who attempted this challenge,” which is directly interpretable, needs only a stored distribution per item, and is exactly what the original proposal specified — “benchmarked against the anonymised performance distribution of prior candidates.” Items with too few attempts report a wide interval rather than a false precision.

4.5 Integrity monitoring

Paste-burst detection, long-idle-then-large-insert patterns, tab-focus loss, and the same rule-based generated-code signals from M3 applied to the submission’s edit trace. Reported as an integrity confidence alongside the score, never as an automatic invalidation.

Operational choices

Default to claude-opus-5 (1M context, $5/$25 per MTok) with adaptive thinking for the reasoning-heavy call sites — L1 and L4 especially. Two levers matter a great deal at this project's volume:

  • Prompt caching. L1's schema, ontology excerpt, and few-shot block are a large stable prefix. Put them first, cache them, and verify with usage.cache_read_input_tokens — anything varying inside that prefix silently kills the hit rate.
  • Batch API. Corpus backfills and evaluation runs are not latency-sensitive and run at 50% cost. Every dataset build in §10 should go through it.
  • Prompt versioning. Every LLM-derived record stores model_id and prompt_version in its provenance, so results stay reproducible after a prompt change and you can re-run an ablation honestly.
  • Effort tuning — output_config.effort at high for L4, lower for the mechanical extractions. Worth a small sweep as an appendix; it is a real cost/quality result.

This section is what separates a strong B.Tech project from a working demo. Build M14 early and keep it running — a system with numbers behind it defends itself.

The injected-falsification design is the strongest experimental idea here

You cannot obtain a labelled corpus of real fraudulent CVs — nobody will give you one, and no honest ground truth exists. But if you generate the falsifications yourself, you know exactly what is wrong with every document. That yields per-fraud-type detection rates at a fixed false-positive rate on clean CVs, which is precisely the table a reviewer wants to see, and it is entirely achievable.

Metrics

  • Extraction — claim-level precision/recall/F1; span-grounding violation rate.
  • Detection — per-fraud-type recall at fixed FPR; overall AUC; the FPR on clean documents is the number that actually matters.
  • Authorship — separation between self-distances and the empirical null (ROC over the reference corpus, equal error rate); degradation under formatting; abstention rate on thin profiles.
  • Calibration — reliability diagrams, expected calibration error, Brier score. "When we say 80%, is it right 80% of the time?" is the question the whole confidence framing rests on.
  • Ranking — nDCG@k for recruiter search against expert-ranked candidate sets.
  • Ablation — remove each evidence stream in turn and measure the drop. This table directly proves or refutes the multi-source thesis.
  • Fairness — false-positive rate disaggregated across subgroups (see §13). A gap here is a finding to report, not a failure to hide.

12Sequencing

Assuming roughly 34 working weeks. The ordering is deliberate: the standalone product first, the research core second, the commerce layer last and deliberately thin.

W1–3
Phase 0 — Contracts and spikes

OpenAPI specs for M1/M5/M6, the EvidenceEvent schema, architecture decision records, monorepo and CI scaffolding. Four throwaway spikes: gVisor isolation, tree-sitter multi-language extraction, structured-output extraction against a real CV, Neo4j propagation query. No product code.

W4–9
Phase 1 — CV Verification vertical

M5 complete, plus the minimum of M0/M1 to support it. Ship it as a standalone API with its own docs. Build the injected-falsification corpus alongside — not after. First real metrics by week 9.

W10–16
Phase 2 — Code provenance and skill graph v1

M3 through authorship verification; M6 scoring engine with the fusion model. The formatter-robustness experiment lands here. First cross-modal consistency rules — commit activity checked against CV claims — connect M3 to M5.

W17–23
Phase 3 — Assessment engine

M4 including the sandbox, the synthesis validation gate, and the cohort study that builds the per-item percentile tables. Recruit volunteers early; this phase has an external dependency on people’s time and it will be the schedule risk.

W24–29
Phase 4 — Marketplace and commerce

M7–M10, deliberately thinner than the rest. Razorpay sandbox, escrow state machine, a financing model that is honest about being a demonstration. Timeboxed hard — this is the de-scope reservoir.

W30–34
Phase 5 — Enterprise surface and the report

M11–M13, full ablation study, calibration report, fairness audit, thesis writing. Reserve the last three weeks entirely for evaluation and writing — the difference between a good project and a good defence is made here.

De-scope order, decided now rather than in a panic

  1. Financing risk model → replace with a documented static advance rate
  2. Real ATS connectors → keep the mock ATS only
  3. Managed team assembly → drop entirely
  4. Marketplace bidding sophistication → direct-award only
  5. Multi-language breadth in M3 → narrow to Python and JavaScript, well
Never cut

The evaluation harness, the calibration study, and the ablation table. A project with three working modules and rigorous numbers defends better than one with fifteen modules and no evidence any of them work.

14Open decisions

Everything above holds under the stated assumptions. These are the questions whose answers would actually change the plan — worth settling before Phase 0 begins.

Team size and duration

The sequencing assumes roughly 34 weeks and 3–4 people working in parallel across module boundaries. A solo project or a single semester changes the module count substantially — probably to M5 + M3 + M6 only, with the marketplace dropped entirely.

Does the evaluation need to reach publication standard?

If a paper is a goal, the formatter-robustness study and the calibration analysis should expand and the marketplace should shrink further. If the department weights the working system more heavily, the balance shifts the other way. This is the single biggest fork in the plan.

Where does the corpus come from?

Access to real CVs — a placement cell, an alumni network, willing classmates — determines whether the injected-falsification experiment is realistic or purely synthetic. Worth resolving in week 1, because it has the longest lead time of anything here.

Is deployment part of the assessment?

If the panel expects a live system, k3s and real infrastructure enter scope and cost several weeks. If a local demo suffices, Docker Compose is enough and those weeks go to evaluation instead.

LLM budget ceiling

Corpus-scale extraction runs are the dominant cost. Batch API and prompt caching bring it down substantially, but a hard ceiling would change which call sites use which effort settings — worth knowing before the evaluation runs are designed.
