DevBridge M5 — Two-Person Build Plan

CV Verification Buildout

The standalone verification engine, split into two tracks that can be built in parallel from week one and integrated without either person waiting on the other. One seam, one contract, two owners.

Module M5 — cv-verification Team 2 Span ~16 weeks Training none

01What "standalone" has to mean

Three constraints define this module. Everything else in the plan follows from them, and violating any one turns a product back into a feature.

  1. It runs on any CV. A document from someone with no DevBridge account, no connected repositories, and no platform history must produce a complete, useful report. Anything the platform adds is an enhancement, never a prerequisite.
  2. It imports nothing from the platform. No marketplace models, no shared database, no internal calls. Whatever it needs from other modules arrives through its public request body — which means an enterprise customer can supply the same thing.
  3. It emits findings, never verdicts. Output is a structured set of discrepancies with calibrated confidence and source provenance. No score threshold, no pass/fail, no hiring recommendation.
How platform evidence enters without creating a dependency

Cross-referencing CV claims against commit history is the highest-value rule in the catalogue — but M3 will not exist for months, and enterprise customers will never have it. So the verification request carries an optional external_signals block. When it is present, the commit-reconciliation rules fire. When it is absent, those rules abstain explicitly and say so in the report. M5 never calls M3; M3 (or a customer's own ATS) supplies the data as input.

02The seam

A two-person project succeeds or fails on where you cut it. There is exactly one good cut here, and it falls between understanding the document and judging it.

Track A — Person 1

Understanding

Bytes in, a validated ClaimGraph out. Owns everything where language is ambiguous and a model is doing the reading.

  • 5.1doc-ingest — layout-aware extraction, reading order, offset map
  • 5.2claim-extractor — text → typed claims with enforced spans L1
  • 5.3entity-resolver — embedding retrieval + closed-set tie-break L2
  • 5.6bnarrative-renderer — findings → recruiter-readable prose L3
Track B — Person 2

Judgement

A ClaimGraph in, a findings report out. Owns everything that must be deterministic, testable, and defensible line by line.

  • 5.4consistency-engine — the rule catalogue and interval logic
  • 5.5external-attestation — VC verifier, issuer connectors, reference issuer
  • 5.6afinding-aggregator — confidence composition, report assembly
  • 5.0service shell — API, jobs, storage, metering, tenancy, CI

ClaimGraph — the one interface between them

Track A produces it. Track B consumes it. Nothing else crosses. It is designed and frozen in week 1, before either person writes implementation code, and it ships with hand-authored golden fixtures covering every claim type and every edge case the rules will need.

ClaimGraph {
  graph_id, schema_version, document_id,
  source: { pages, char_count, ingest_method, ocr_used },
  claims: [ Claim ],
  extraction_meta: { model_id, prompt_version, input_hash,
                       span_failures, retries, extracted_at }
}

Claim {
  claim_id, kind: employment | education | certification | project | skill,
  interval: { start: {y, m?}, end: {y, m?} | "present",
               precision: exact | month | year | open },
  attributes: { org?, title?, degree?, issuer?, credential_id?, skill_refs[] },
  provenance: { char_start, char_end, page, verbatim },
  resolution: { canonical_id?, registry?, score, status: resolved | ambiguous | unresolved },
  flags: [ date_imprecise, employment_type_unstated, ... ]
}
The fixtures are the real deliverable of week 1

Roughly twenty hand-written ClaimGraph JSON files, committed to the repository: a clean CV, one with overlapping employment, one with an anachronistic skill claim, one with year-only precision throughout, one with an unresolvable employer, one with nothing but projects. Track B builds the entire rule engine against these and never once needs Track A's extractor to be working. That is what buys genuine parallelism instead of one person waiting.

03Track A — Understanding LLM

5.1 doc-ingest deterministic

Deterministic work, but it belongs to A because extraction quality depends on it and the two must be tuned together.

  • Text and geometry — PyMuPDF for text with bounding boxes; pdfplumber as a cross-check on tables.
  • Reading order — the actual hard problem. Two-column résumés interleave catastrophically under naïve extraction. Recursive XY-cut segmentation, or x-coordinate clustering into columns then top-to-bottom within each.
  • DOCX — parse the structure rather than flattening to text; headings and list nesting are signal.
  • Scanned documents — PaddleOCR, with a confidence floor below which the document is rejected rather than guessed at.
  • Section segmentation — heuristics on font size, weight, and heading vocabulary. Cheap, and it measurably improves extraction by giving the model explicit structure.

Output contract: normalised text plus a char_index → (page, bbox) map. That map is load-bearing — it is what lets the UI highlight the exact region a claim came from, and it is what makes span grounding verifiable rather than decorative.

5.2 claim-extractor L1

A whole résumé fits in context with enormous room to spare, so there is no chunking, no retrieval, no windowing. One call, one document, strict schema.

Span grounding — the core guarantee

Every claim must carry the verbatim text it came from, and that text is verified to exist in the source before the claim is accepted. A fabricated employer cannot survive the check.

for each returned claim:
  norm = NFKC(collapse_whitespace(claim.verbatim))
  if norm in normalised_source:
      recover char offsets → accept
  elif fuzzy_ratio(norm, best_window) > 0.92:
      accept with flag span_recovered
  else:
      reject claim → retry once with the failures named
      → still failing: drop claim, record span_failure
The detail that decides whether this works in practice

Naïve exact matching fails constantly on real PDFs — ligatures, non-breaking spaces, soft hyphens, and inconsistent whitespace from the extractor. Normalise both sides (NFKC, whitespace collapse) before comparing, and keep a fuzzy tier above it. Skip this and you will reject a third of your correct claims and conclude the model is hallucinating when it is not.

Deterministic post-validation no model

Runs on every extraction before the ClaimGraph is released. Catches what span grounding cannot: dates that fail to parse, intervals ending before they start, dates in the future, present on more than one full-time role, empty required attributes, claim types that contradict their source section.

5.3 entity-resolver L2

Retrieval first, model second, and the model only ever chooses from a closed set.

  1. Embed the surface form; retrieve top-k from the registry via pgvector.
  2. If the top candidate clears an absolute threshold and beats the runner-up by a margin — accept, no model call. This is most cases.
  3. Only when the top two are close: one model call, given only those candidates plus an explicit abstain option.
  4. Nothing clears threshold — status unresolved. An honest unknown beats a confident wrong canonical ID.

Registries: ESCO for skills (free, downloadable, multilingual). AICTE and UGC publish institution lists for India. Employers are the hard one — seed from a public company registry and accept that the long tail stays unresolved.

5.6b narrative-renderer L3

Input is the findings JSON and nothing else — never the CV, never the ClaimGraph. The model cannot introduce a fact it was not given if it was never given the document.

Faithfulness is checkable automatically

Extract every numeral and every date from the generated prose and assert each one appears in the findings JSON. Assert every paragraph cites at least one finding ID. Both are a few lines of code, both run in CI on every prompt change, and together they catch the failure that matters — prose that sounds authoritative about something nobody computed. If validation fails twice, fall back to a deterministic template. The report must render even when generation does not.

04Track B — Judgement deterministic

5.4 consistency-engine

The intellectual core of this half, and the part that most rewards being built carefully.

Intervals are imprecise, and pretending otherwise is the classic bug

"2021–2023" does not denote an interval. It denotes a set of possible intervals. Every date is stored as a bound pair, and every relation resolves to one of three answers rather than a boolean:

FuzzyInterval { start_min, start_max, end_min, end_max }

overlap(A, B) → DEFINITE   overlaps under every consistent reading
              → POSSIBLE   overlaps under some readings
              → NONE       disjoint under every reading

Only DEFINITE ever raises a discrepancy.
POSSIBLE is recorded, surfaced as context, and never scored.

Getting this right is what separates a rule engine that is trusted from one that cries wolf on every year-only résumé — which is most of them.

Rule catalogue

IDRuleBasisStrength

R11 and R12 are deliberately non-scoring

These two encode career-shape assumptions that penalise caregiving breaks, illness, non-linear paths, and non-Western title ladders. They stay in the system because a human reviewer may reasonably want to see them — but they are displayed only, never aggregated into any confidence figure, and the engine enforces that structurally: a rule declares scoring: false and the aggregator cannot include it. Making this a property of the code rather than a paragraph in the report is the difference between a stated principle and an enforced one.

Rule interface

Every rule is a pure function with the same shape, registered declaratively. Adding a rule means adding one file and one fixture — never touching the engine.

Rule {
  id, version, severity_class, scoring: bool,
  requires: [ claim_kinds, external_signals? ],
  evaluate(graph, signals) → [ Discrepancy ] | ABSTAIN(reason)
}

Discrepancy {
  rule_id, rule_version, severity, confidence,
  claim_refs[], params, explanation_template
}

Explicit abstention is not a detail. A rule that cannot run must say so and say why, and the report must show it — "commit reconciliation: not evaluated, no activity data supplied" is information a recruiter needs. Silence reads as a pass.

Where confidence comes from without any fitting

Each rule derives its own confidence from a documented formula over the evidence in front of it. No global weights, no learned parameters:

  • R3 anachronism — 1.0. The technology's release date is a fact.
  • R1 overlap — scales with the overlap fraction that holds under every consistent date reading. Total overlap under all readings approaches 1.0; a marginal one stays low.
  • R5 arithmetic — scales with the size of the discrepancy relative to date imprecision.
  • R8 registry miss — capped low by construction, because registry incompleteness is far more likely than a fabricated institution.

5.5 external-attestation

  • W3C Verifiable Credentials 2.0 verifier — signature validation, issuer DID resolution, expiry, revocation status.
  • Reference issuer — a small companion service that issues signed VCs for degrees and certificates. This is how you demonstrate the whole trust path without a single institutional partnership, and implementing the protocol is a stronger result than borrowing one API key.
  • Real integrations that are actually obtainable — Credly and Acclaim expose public badge verification, and Open Badges 3.0 is now aligned with the VC data model. At least one live issuer integration is within reach, and it is worth the effort: it turns the reference issuer from a substitute into a demonstration.

5.6a finding-aggregator

Composes discrepancies into a report without collapsing them into a single number. Per-section confidence, computed by noisy-OR over independent scoring discrepancies within that section. Advisory findings pass through untouched and unweighted. Abstentions are listed as explicit coverage gaps.

Deliberately absent

No overall trust score. No threshold. No colour-coded verdict badge. The temptation to add one will be strong — it demos well — and it converts a defensible evidence report into an indefensible automated judgement. The report's top line is what was checked, what was found, and what could not be evaluated.

5.0 service shell

Unglamorous and entirely B's, because it is what makes the module a product rather than a script: FastAPI with an async job model (202 + webhook), Postgres for graphs and reports, object storage for documents, idempotency keys on every mutating endpoint, per-verification metering, API-key tenancy with a sandbox tier, OpenAPI 3.1 committed before implementation, and CI that fails when the served spec drifts from the committed one.

Two scheduling decisions worth defending

Integration checkpoints are scheduled, not hoped for. Weeks 7 and 13 exist because "we'll integrate when both sides are ready" is how two-person projects discover in week 14 that their schemas never agreed. The freeze at week 13 is real. Three weeks of measurement and writing against a stable system beats five weeks of features and a rushed evaluation — the evaluation is what you are actually graded on.
